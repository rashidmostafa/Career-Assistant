# Deploying the backend to Render

The APK is not self-contained. `EXPO_PUBLIC_API_URL` is compiled into the JS
bundle at build time, and the app opens that URL in a real browser for Google
sign-in. If it points at a LAN IP or an ngrok tunnel, the build stops working
the moment you leave that network. Deploying the backend to a stable public
URL fixes it permanently.

Do these in order. Steps 1–3 can be done from any machine.

---

## 1. MongoDB Atlas — allow Render to connect

Your cluster almost certainly whitelists your home IP only. Render's outbound
IPs are different, and `connectDB()` calls `process.exit(1)` on failure
([server/config/db.js:23](../server/config/db.js#L23)) — so a blocked
connection makes the service **crash-loop on boot** with no obvious cause.
This is the single most common way this deploy fails.

1. Atlas → **Network Access** → **Add IP Address** → **Allow access from
   anywhere** (`0.0.0.0/0`) → Confirm.
   - Safe here because the database still requires user + password. If you'd
     rather lock it down, Render lists static outbound IPs per service under
     **Connect → Outbound**; add those four instead.
2. Atlas → **Database** → **Connect** → **Drivers** → copy the
   `mongodb+srv://...` string.
3. Replace `<password>` with the real DB user password. Forgotten it? Atlas →
   **Database Access** → **Edit** the user → **Edit Password** → Autogenerate.
4. Make sure the database name is in the path, before the `?`:
   `mongodb+srv://user:pass@cluster.mongodb.net/career-assistant?retryWrites=true&w=majority`
   Without it you silently get a database called `test`, and your existing
   accounts appear to have vanished.

## 2. Deploy to Render

The repo has a [`render.yaml`](../render.yaml) blueprint, so this is mostly
clicking through prompts.

1. [dashboard.render.com/blueprints](https://dashboard.render.com/blueprints) →
   **New Blueprint Instance** → connect GitHub → pick `Career-Assistant`.
2. Render reads `render.yaml` and prompts for the `sync: false` values. Fill in:
   - `MONGODB_URI` — from step 1
   - `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` — from step 3 below
   - `SERVER_BASE_URL` — **leave blank for now**, you don't know it yet
   - `ALLOWED_ORIGINS` — leave blank (native apps send no `Origin` header, and
     [server/app.js:57](../server/app.js#L57) treats empty as allow-all)
   - `SMTP_*` — needed for registration OTP emails; skip if you only use Google
     sign-in for now
   - `JWT_SECRET` / `SESSION_SECRET` are generated by Render automatically
3. Apply. First deploy takes ~3 minutes.
4. Copy the service URL, e.g. `https://career-assistant-api.onrender.com`.
5. **Environment** → set `SERVER_BASE_URL` to exactly that URL, **no trailing
   slash** → save. This triggers a redeploy.
   - It matters: [server/config/passport.js:52](../server/config/passport.js#L52)
     builds the Google callback as `${SERVER_BASE_URL}/api/auth/google/callback`.
     A trailing slash produces a double-slash URL that won't match Google's
     whitelist, and sign-in fails with `redirect_uri_mismatch`.
6. Check it: open `https://<your-url>/health` — expect
   `{"status":"ok",...}`.

## 3. Google Cloud Console — authorise the callback

1. [console.cloud.google.com](https://console.cloud.google.com) → your project →
   **APIs & Services** → **Credentials** → your OAuth 2.0 Client ID.
2. Under **Authorised redirect URIs**, add:
   ```
   https://<your-render-url>/api/auth/google/callback
   ```
3. Save. Google's changes can take a few minutes to take effect.
4. The client ID is shown on this page. The client secret is under
   **Additional information**, or download the JSON. Lost it? **Add secret**,
   then use the new one.

> Do **not** add `career-assistant://` or `exp://` as redirect URIs here.
> The server receives Google's callback and deep-links to the app itself
> ([server/routes/auth.js:241](../server/routes/auth.js#L241)).

## 4. Point the app at it and rebuild

The one step that actually has to happen on a machine that can build.

1. Create `.env` in the project root (copy [`.env.example`](../.env.example)):
   ```env
   EXPO_PUBLIC_API_URL=https://career-assistant-api.onrender.com
   ```
2. Rebuild — the old APK cannot be reconfigured, the URL is baked in:
   ```bash
   npx eas build --profile preview --platform android
   ```
   EAS builds in the cloud, so this works from any network.
3. Install the new APK. Google sign-in now works on any network, forever.

## Known rough edges

**First request after idle takes ~50 seconds.** Render's free tier spins the
service down after ~15 minutes of inactivity. The cold start holds the
connection open rather than refusing it, so the request usually succeeds — it
just looks frozen. The client's retry back-off is 500ms/1s/2s
([services/authApiService.ts:78](../services/authApiService.ts#L78)), which
covers a network blip but not a cold boot, so a platform-level fetch timeout
could still surface it as a failure.

Two ways to deal with it:
- Free: point [uptimerobot.com](https://uptimerobot.com) at
  `https://<your-url>/health` on a 14-minute interval to keep it warm.
- $7/mo: Render's Starter plan doesn't sleep.

**Sessions are in-memory.** `express-session` uses the default `MemoryStore`
([server/config/passport.js:97](../server/config/passport.js#L97)), so a
restart mid-OAuth drops the stored `redirectUri` and that one sign-in attempt
falls back to `APP_DEEP_LINK`. Harmless on a single free instance; if you ever
scale past one instance, move this to `connect-mongo`.

**Rotating `JWT_SECRET` logs everyone out.** Render generated it once and keeps
it stable across restarts. Only regenerate deliberately.
